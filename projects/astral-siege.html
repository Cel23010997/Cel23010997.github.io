CONSTRAINED PROJECT / C++ GAME

Astral Siege

Defend Earth in a space tower-defence game where gravity changes the path of a shot.

Game screens & state flowC++ · Alpha EngineThe Alpha Beasts · 5 people
Explore the code

My contribution

My contributions include the application/state loop, game screens, shared menu work, pause/options interactions and Earth-related work. I also refined restart state and resource cleanup. Gameplay, weapons, enemies, art and audio were developed collaboratively across the team.

The problem

A game needs more than a combat loop. Players also need to move between menus, gameplay, pause, results and a fresh attempt without carrying stale interaction state or leaving resources behind.

The constraint

The original game used a Windows C++ engine with manually managed meshes and explicit game-state load, initialise, update, draw, free and unload stages. Interface work had to fit that lifecycle and the rest of the team’s systems.

What I checked

The browser build was checked for asset loading, main-menu entry, starting gameplay and pause controls. I also traced the reset, menu-navigation and mesh-lifetime changes in the original commits and compared them with the submitted source. The evidence below describes concrete code behaviour; it does not claim a measured memory-leak reduction or a formal usability study.

What failed

Mesh cleanup freed slots without clearing the stored pointers, so later cleanup could encounter stale pointers. Game reset also left HUD interaction flags behind. In menus, Escape previously requested application exit instead of navigating back.

What changed

In 0d12adc, I guarded mesh cleanup with a null check and cleared each slot after freeing it. In 307d0b0, I added HUD::Reset() to clear the counter, click state and hover flags during game reset. In 2813865, eligible menu states return to the previous state on Escape.

The outcome

Already-cleared mesh slots are skipped during repeat cleanup; restart explicitly resets HUD state; and menu Escape handling returns to the previous screen. These are outcomes supported by the source changes. They show the less visible work that makes a game’s surrounding interactions coherent.

Browser edition

The portfolio port compiles the original C++ game code to WebAssembly and uses an independently written WebGL, input and browser-audio compatibility layer. The proprietary Alpha Engine SDK is excluded. This is a later adaptation for the portfolio, separate from the original team submission.
